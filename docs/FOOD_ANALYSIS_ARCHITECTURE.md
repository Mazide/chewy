## Что уже сделано

Реализован отдельный локальный стенд в `server/`: Python 3.11+, стандартная
библиотека, SQLite, один HTTP-процесс и последовательный обработчик задач.
Команды, API, ограничения, схема результата и хранение — [server/README](../server/README.md).

Файлы: `app.py` — API/обработчик; `store.py` — очередь и ревизии в SQLite;
`analyzer.py` — mock, Gemini и валидация; `submit.py` — отправка фото из терминала.
Ключ Gemini только в окружении. Mock включён явно по умолчанию и не изображает
распознавание: возвращает `insufficient_evidence` с неизвестными направлениями.

Проверены 37 тестов, включая настоящий HTTP/CLI-проход на localhost, конкурентные
повторы, перезапуск, сохранение прежнего результата, отмену/удаление во время
анализа и временную ошибку записи в SQLite. Последняя проверка всех тестов успешна:

```bash
python3 -m unittest discover -s server -t . -v
```

Настоящий вызов Gemini и качество оценки еды **не проверены**. Стенд не подключён
к Storybook или iOS. Награды, герой и дневная сводка сервером не управляются.
Старый нативный `FoodAnalyzer.swift` и `scripts/gemini-benchmark.mjs` не перенесены
на новый контракт; их ккал/БЖУ или взаимоисключающие сектора не являются целевой схемой.

## Целевая логика

```text
Клиент: фото + необязательные уточнения + локальное сохранение
  → Chewy API: проверка входа, идентификация, лимиты, идемпотентность
  → надёжное сохранение снимков и задачи → очередь
  → один мультимодальный запрос со всеми фото записи
  → структурированные наблюдения → валидация → правила оценки
  → сохранённый результат → клиент/Сегодня/дневной вклад
```

AI извлекает составляющие и неопределённость. Прикладной код подтверждает вклад
по наблюдениям. Монеты и учёт дня независимы от ответа модели. Реплики героя
выбираются из утверждённых шаблонов. Все снимки передаются вместе: повторный
ракурс не должен автоматически считаться дополнительной порцией.

Четыре направления — белок, углеводы с клетчаткой, ненасыщенные жиры, овощи/фрукты —
независимы, не складываются в 100% и не являются суточными нормами. Один продукт
может дать несколько вкладов. Визуальные сектора тарелки, если потребуются,
описываются отдельно; площадь продукта на фото не равна доле нутриента.
Неизвестные масло/соль/сахар не угадываются. Structured output гарантирует форму,
но не доказывает правильность распознанного продукта.

## Сохранение и протокол

Основные сущности: запись еды, неизменяемый снимок её входных данных, задача,
результат. В локальной базе снимок входа хранится внутри задачи. У записи два
указателя: принятый результат и ожидающий анализ. Дата фиксируется при добавлении
первого фото, включая импорт из галереи, а не по EXIF или моменту ответа модели.

`Idempotency-Key` связывает повторную отправку с исходной задачей. Новые правки
создают новую ревизию той же записи. Пока она обрабатывается, остаются доступными
прежние результат и фото. Ошибка сохраняет также новые входные данные для повтора.
Успех атомарно заменяет прежний результат, включая переход к `non_food`.

Отмена, удаление или более новая ревизия запрещают применение старого ответа.
Проверяются текущая задача и уникальный маркер попытки. Отмена не гарантирует
возврата стоимости уже начавшегося вызова. Удаление исключает дневной вклад,
но не отзывает монеты, учёт дня и постоянный прогресс. Поздний ответ относится
к исходному дню записи. Сервер анализа хранит сведения; игровое применение
должен выполнить отдельный клиентский слой по DESIGN.

Сохранение на телефоне и приём сервером — разные состояния. До завершения загрузки
нельзя обещать, что облако уже выполняет анализ. После приёма задачи сервером
открытый экран/приложение не нужны. При локальном сервере компьютер и процесс
должны работать; во время остановки очередь ждёт. Push не является условием
сохранения результата, для начала достаточно запроса статуса при возвращении.

## Кандидаты API-провайдеров

Проверено по официальной документации 29.10.2026; перед интеграцией проверить
актуальность и доступность для аккаунта. Это кандидаты для одинакового бенчмарка,
не доказанный рейтинг точности на еде.

| Кандидат | Предложенная роль | Стандартные вход/выход за 1 млн токенов на дату исследования |
|---|---|---|
| `gemini-3.8-flash` | Исходный кандидат, выбранный default локального адаптера | $0.75 / $3.75 до конца 2026; объявлены $1.50 / $7.50 с января 2027 |
| `gemini-3.5-flash-lite` | Более дешёвый кандидат Google | $0.30 / $2.50 |
| `gpt-6-luna` | Альтернативный кандидат OpenAI; адаптер пока не реализован | $0.10 / $0.50 |

Источники: [Gemini Flash](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-flash),
[Flash-Lite](https://ai.google.dev/gemini-api/docs/models/gemini-3.5-flash-lite),
[цены Google](https://ai.google.dev/gemini-api/docs/pricing),
[OpenAI Docs: GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna).
Стоимость фото измерять по реальному usage: изображения, reasoning и повторные
попытки не равны фиксированной цене одного снимка.

В первую версию предлагался один прошедший бенчмарк провайдер. Резерв включать
после проверки, при технической недоступности, а не при любой неопределённости.
Вторая модель тоже не видит скрытый рецепт. Специализированную базу нутриентов
и API подсчёта калорий для нынешнего контракта добавлять не предлагалось.

Выбор Gemini Developer API требует проверки возрастной аудитории и стран запуска:
на дату исследования условия ограничивали приложения, направленные на или
вероятно доступные младше 18 лет, и требовали paid services для пользователей
EEA/UK/Швейцарии. Платный режим не означает нулевого хранения. Для возможного
OpenAI Responses использовать `store:false`, также не обещая zero retention.
[Условия Google](https://ai.google.dev/gemini-api/terms),
[OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data).

## Если потребуется облако

Предложен Firebase/Google Cloud: Functions для API/обработчика, Cloud Tasks для
очереди, Firestore для задач/результатов, закрытый Cloud Storage для фото,
Anonymous Auth + App Check/App Attest, Secret Manager для ключей. Альтернатива —
Cloudflare Workers + Queues + D1 + R2. Выбор и развёртывание не выполнены.

Обычный прокси скрывает ключ, но сам по себе не обеспечивает сохранённую задачу,
получение результата после закрытия приложения, версии и отмену. Firebase AI Logic
имеет managed proxy и серверные шаблоны, однако эти обязанности Chewy сохраняются.
[Firebase task functions](https://firebase.google.com/docs/functions/task-functions),
[server prompt templates](https://firebase.google.com/docs/ai-logic/server-prompt-templates/get-started).

При переносе сохранить текущую семантику API. Фото можно загружать отдельно,
а постановку в облачную очередь связать с надёжным сохранением и восстановлением
незавершённой отправки. Повторная доставка задачи не должна повторно применять
результат. Идентификация пользователя и проверка владельца обязательны для
публичного сервиса; локальный стенд обслуживает только доверенный loopback.

Остаются отдельными решениями: сроки хранения фото, восстановление истории после
переустановки, аккаунт, публичные квоты и лимит расходов. Логи должны содержать
идентификаторы/версии/ошибки/задержки/usage, без снимков и заметок пользователя.
Локальный стенд пока хранит данные до явного удаления, не реализует облачный TTL.

## Продолжение без этого чата

Актуальный статус и ближайшая проверка этого направления записаны в TODO;
команды работы — server/README. Для выбора модели нужен набор реальных блюд:
смешанные блюда, перекусы, соусы, плохой свет, повторные ракурсы, не-еда и правки.
Сравнивать распознавание направлений, выдуманные ингредиенты, честную неопределённость,
задержку и фактический расход. Пороги продуктовой VALIDATION не менять.

Запуск из корня проекта: `python3 -m server.app`. Если процесс после закрытия чата
остановится, эта команда снова поднимет его с той же базой `server/.data/`.
Сохранность файлов не зависит от работающего процесса. Код и документы записаны
на диск; коммит и push в рамках этого обсуждения не выполнялись.
