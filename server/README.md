# Локальный сервер анализа Chewy

Один процесс Python и SQLite, без внешних зависимостей, Docker и облачной очереди.
Это отдельный стенд для проверки протокола и будущего бенчмарка. Storybook и iOS
пока не подключены; правила наград и утверждённые продуктовые пороги не меняются.
Схема наблюдений и промпт — технический черновик, качество распознавания ещё не измерено.
Обоснование архитектуры и кандидаты API сохранены в
[FOOD_ANALYSIS_ARCHITECTURE](../docs/FOOD_ANALYSIS_ARCHITECTURE.md); статус — в TODO.

## Запуск

Из корня репозитория, Python 3.11+ на macOS или Linux:

```bash
python3 -m server.app
```

Проверка: [http://127.0.0.1:8787/health](http://127.0.0.1:8787/health).
Остановка — Ctrl+C. Повторный запуск продолжает сохранённые задачи. Пока компьютер
спит или процесс выключен, анализ не выполняется, но данные остаются в SQLite.

По умолчанию используется **mock**: сетевых запросов к модели нет, результат явно
содержит `insufficient_evidence` и четыре `unknown`. Это проверка транспорта и
сохранения, а не фиктивное распознавание содержимого снимка.

Для реального анализа передать `GEMINI_API_KEY` через окружение процесса и запустить:

```bash
python3 -m server.app --provider gemini
```

`.env` и нативный `Secrets.plist` автоматически не читаются. Ключ не сохраняется в
базе и не выводится в логи. Модель по умолчанию — `gemini-3.8-flash`; другую можно
выбрать через `--model` или `GEMINI_MODEL`. Новые задачи получают выбранную модель,
ранее принятые сохраняют свою. Запуск в mock обрабатывает только mock-задачи;
сохранённые Gemini-задачи ждут запуска с `--provider gemini`.

Порт меняется через `--port`, отдельная база — через `--data-dir`.
Один каталог данных может обслуживаться только одним процессом.

## Отправить фото

Во втором терминале из корня проекта:

```bash
python3 server/submit.py /absolute/path/meal.jpg --time-zone Europe/London --wait
```

Несколько кадров одной записи и добровольные уточнения:

```bash
python3 server/submit.py /absolute/path/plate.jpg /absolute/path/detail.jpg \
  --name "Обед" --notes "В заправке оливковое масло" \
  --time-zone Europe/London --wait
```

CLI печатает `meal-id`, `idempotency-key` и JSON задачи. Без `--wait` он завершится
после приёма задачи сервером. Прекращение ожидания не отменяет обработку.

Для уточнения передать `--meal-id` существующей записи и **полный актуальный набор
фото и текстовых полей**. Старые поля автоматически не объединяются с новыми.
Исходная дата и часовой пояс при этом читаются с сервера и сохраняются.
Повтор неизменного запроса после потери ответа — тот же `--meal-id` и
`--idempotency-key`. Явный повтор после ошибки — тот же `--meal-id`, новый ключ.

Для новой записи CLI по умолчанию использует UTC; `--time-zone` задаёт IANA-зону.
Время первого добавления фиксируется при запуске CLI, не берётся из EXIF.

Принимаются JPEG/PNG/WebP: до шести кадров, до 3 MiB на кадр и 18 MiB на весь JSON.
CLI отправляет файлы как есть, без уменьшения или удаления EXIF; для этого стенда
нужно заранее подготовить копии фотографий. Нативная подготовка изображений —
отдельный шаг. Проверка сигнатуры файла не заменяет полноценное декодирование изображения.

## HTTP-контракт

Все пути относительно `http://127.0.0.1:8787`.

| Метод и путь | Результат |
|---|---|
| `GET /health` | Состояние процесса и выбранный провайдер |
| `POST /v1/meals/{mealId}/analyses` | Сохраняет фото и задачу одной транзакцией; `202` с объектом задачи |
| `GET /v1/jobs/{jobId}` | Статус, ошибка или готовый результат, метаданные фото и уточнения |
| `GET /v1/meals/{mealId}` | Исходные дата/зона, `acceptedJob` и `pendingJob` |
| `GET /v1/jobs/{jobId}/photos/{photoId}` | Фото конкретной ревизии |
| `POST /v1/jobs/{jobId}/cancel` | Отменяет ожидающую задачу; поздний ответ не применяется |
| `DELETE /v1/meals/{mealId}` | Удаляет фото, уточнения и результаты всех ревизий; сохраняет отметку удаления |

Создание анализа требует `Content-Type: application/json` и `Idempotency-Key`.
`mealId` содержит 1–80 символов `A-Z a-z 0-9 _ -`; ключ — 1–128 таких символов.

```json
{
  "firstPhotoAddedAt": "2026-10-29T12:00:00+00:00",
  "localDate": "2026-10-29",
  "timeZone": "Europe/London",
  "photos": [
    { "id": "photo-1", "mimeType": "image/jpeg", "dataBase64": "<base64 bytes>" }
  ],
  "userInput": { "dishName": "Обед", "notes": "", "portion": "" }
}
```

Состояния задачи: `queued → running → succeeded | failed | cancelled`.
Временная ошибка провайдера возвращает задачу в `queued`, максимум три попытки
с задержкой. Прерванная при выключении задача восстанавливается при запуске;
бюджет попыток тоже сохраняется. Если ответ потерян между провайдером и локальной
базой, после аварии возможен повторный оплачиваемый вызов — гарантия однократности
относится к применению результата, а не к биллингу внешнего API.

Одинаковые ключ и запрос возвращают прежнюю задачу, включая её конечный статус.
Тот же ключ с другим содержимым даёт `409`. Новая отправка с новым ключом создаёт
следующую ревизию той же записи и отменяет её прежнюю незавершённую задачу.
Изменить исходные дату/время/зону нельзя. Удалённая запись возвращает `410` и
не восстанавливается повтором запроса.

Прежний принятый результат и его фото сохраняются при ожидании, ошибке и отмене
уточнения. Успешный ответ, в том числе `non_food`, заменяет принятый результат.
Сервер не выдаёт награды и не управляет героем.

## Содержимое результата

`outcome`: `food`, `non_food` или `insufficient_evidence`. В `components` —
распознанные составляющие, источник `image`/`user`, ссылки на снимки и степень
определённости. `unknowns` сохраняет то, чего нельзя установить.

`assessment.directions` содержит `protein`, `fiberRichCarbs`, `unsaturatedFats`,
`vegetablesFruit`, каждое — `present`, `not_observed` или `unknown`.
Это независимые направления, не доли тарелки и не суточные нормы. Валидатор
подтверждает `present` только при ясном подтверждающем компоненте, но не может
доказать, что модель правильно распознала сам продукт. Неизвестное масло или
состав не подменяются нулём. Калории, граммы, баллы и реплики героя не запрашиваются.

`provenance` фиксирует провайдера, модель, версии промпта и правил. Адаптер передаёт
все снимки одним запросом. Дата записи остаётся в базе и модели не отправляется.
Формат Gemini сверён с [документацией structured outputs для generateContent](https://ai.google.dev/gemini-api/docs/generate-content/structured-output).

## Данные и границы стенда

SQLite с фото, запросами и результатами находится в `server/.data/`, исключённом
из git. Автоматического срока удаления нет: данные хранятся до удаления записи
или очистки каталога при остановленном сервере. При удалении остаются служебные
идентификаторы/даты и хеш запроса против повторного восстановления; содержимое
фото, уточнений и ответов очищается. Удаление локальных данных не управляет
хранением у внешнего провайдера или копиями базы.

Сервер слушает только `127.0.0.1`, без пользовательских аккаунтов и TLS. Разрешены
браузерные обращения с HTTP-origin `localhost`/`127.0.0.1`; внешний Host/Origin
отклоняется. Это инструмент для доверенного компьютера, не публичный сервис.
Локальный симулятор сможет обращаться по loopback; физический iPhone не видит
loopback компьютера. Доступ из сети потребует отдельной настройки транспорта
и авторизации. iOS/Storybook-клиент в этой работе не подключался.

## Проверка

```bash
python3 -m unittest discover -s server -t . -v
```

Тесты используют временные базы и localhost; внешние API не вызываются.
Проверяются идемпотентность, перезапуск, бюджет повторов, смена ревизий, сохранение
прежнего результата, отмена/удаление во время вызова модели, ошибка записи в БД,
валидация ответа Gemini и реальная отправка через CLI в mock-сервер.
Проверка с настоящим Gemini и бенчмарк качества ещё не выполнены.
