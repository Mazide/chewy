# Офлайн-бенчмарк анализа еды

Отдельная работа от подготовки продуктового ревью. Сервер и прототип не изменены.
Сетевых вызовов в `bench.py` нет. Python 3.11+, без сторонних пакетов. Запуск из
корня репозитория. Контракт берётся непосредственно из `server/analyzer.py`;
изменение внутреннего валидатора может потребовать адаптации инструмента.

## Быстрая проверка

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s benchmarks/food-analysis -p 'test_*.py' -v
python3 benchmarks/food-analysis/bench.py inventory
python3 benchmarks/food-analysis/bench.py check benchmarks/food-analysis/examples
```

Последняя команда проверяет **синтетические** ответы. `contract_checked` означает
прохождение технических и размеченных проверок, не точность распознавания.
Ручное ревью остаётся `pending`. Поле `qualityEvidence` всегда false: программа
не проверяет достоверность происхождения ответа или истинность ингредиентов.
Код выхода `check`: 0 — все ответы прошли автоматические проверки; 1 — есть
ошибка, отсутствующий ответ или лишний JSON; 2 — ошибка входа/CLI. Отсутствие
ручного ревью видно в отчёте, но не меняет технический код выхода.

## Что подготовлено

11 сценариев в `cases.json`: простая тарелка, смешанное блюдо, точный повтор фото,
неразборчивый кадр, скрытое масло, явное уточнение масла, не-еда, порция без состава,
недоверенная инструкция, два демоблюда. Это сценарии, не репрезентативная выборка.

После визуального просмотра демотарелки отмечены видимые овощи и нут; у каши —
ягоды и овсяные хлопья. Точный рецепт, конкретное масло, соль, сахар и молочная
основа неизвестны. Разметка не требует точных названий сортов или рецептов.
Четыре направления независимы. Нет балла питания, нормы или порога выпуска.
Продуктовые пороги `docs/VALIDATION.md` не меняются и не используются как пороги AI.

Происхождение доступных фото: `docs/ASSETS.md`, `prototype/src/core/study-generation.json`.
`meal.png` и `breakfast.png` сгенерированы для демо, не реальные приёмы пищи.
`chicken.jpg` найден, но исключён из эталонного набора: это старый placeholder,
подтверждённого рецепта/происхождения для оценки недостаточно. Скриншоты UI и
анимационные атласы не считаются фото еды. Новые внешние изображения не скачивались.

`inventory` показывает отсутствующие файлы и SHA-256 доступных. Дублированный
`meal.png` проверяет точный повтор; он не заменяет два разных ракурса. Все фото
одного сценария подаются вместе. Для существующих фото ID совпадает с SHA-256
в `server/submit.py`, чтобы импортированный реальный ответ проходил проверку
ссылок. Только намеренный дубликат получает суффикс к хешу. Для синтетических
случаев с отсутствующим фото используются временные `photo-N`. Сопоставление ответов baseline
и clarification/same-meal — ручное, подсказки находятся в `humanReview` и `relation`.

## Материалы для настоящего набора

Поместить собственные подготовленные копии без EXIF в `photos/` (исключены из git):

- `simple-plate.jpg`: читаемые отдельные яйцо, овощи и цельная крупа;
- `mixed-dish.jpg`: суп, рагу или запеканка; известный владельцу рецепт хранить
  отдельно от видимых наблюдений, не выдавать скрытый рецепт за видимое;
- `unreadable.jpg`: кадр, где действительно невозможно определить еду;
- `non-food.jpg`: читаемый предмет без еды и пищевых надписей;
- два разных ракурса одной реальной тарелки — обновить repeated-view и baseline;
- реальные аналоги демотарелки, каши и сценария масла.

JPEG/PNG/WebP, до 3 MiB на кадр и до шести кадров. До реального прогона вручную
проверить фотографии, ожидаемые направления и происхождение; после замены
демоматериалов изменить `material` и пути в собственной копии `cases.json`.
`real-owner` использовать только для реальных собственных фото, не для генераций.
`--cases /path/to/cases.json` указывается перед подкомандой. Подготовленные
запросы содержат фото и пользовательские заметки: хранить локально.

## Будущий настоящий прогон

Сейчас Gemini **не вызывался**. Команды ниже для отдельного явно разрешённого
реального прогона. Сервер на Gemini может расходовать деньги, включая повторы;
ключ передаётся только через окружение по инструкции `server/README.md`.

Сначала запустить существующий сервер в отдельном терминале:

```bash
python3 -m server.app --provider gemini --data-dir /tmp/chewy-food-benchmark-server
```

Один демослучай через существующий CLI (подаёт все кадры записи одним запросом):

```bash
python3 server/submit.py prototype/public/assets/screen-studies/meal.png --time-zone Europe/London --wait > /tmp/chewy-demo-meal-job.json
```

CLI пишет JSON в stdout, служебные ID — в stderr. Для уточнения использовать
`--meal-id` из первого запуска и полный набор фото; для oil-clarification добавить
`--notes 'В заправке оливковое масло.'`. Для двух разных реальных ракурсов передать оба файла. **Точный дубликат
из repeated-view через submit.py не отправлять**: CLI отвергает одинаковые байты.
Для него подготовить JSON и отправить непосредственно в API (только при отдельно
разрешённом реальном прогоне и уже запущенном сервере):

```bash
python3 benchmarks/food-analysis/bench.py prepare repeated-view --output /tmp/chewy-repeat-request.json
curl --fail-with-body -X POST http://127.0.0.1:8787/v1/meals/bench-repeat-01/analyses -H 'Content-Type: application/json' -H 'Idempotency-Key: bench-repeat-01' --data-binary @/tmp/chewy-repeat-request.json
```

Ответ POST содержит `id` задачи; получить её через `GET /v1/jobs/{id}` после
завершения и сохранить JSON в файл для import-job. Ответ со статусом queued
или running ещё нельзя импортировать. Для следующего независимого прогона
выбрать новые meal ID и Idempotency-Key, для транспортного повтора — прежние.
Название/notes/portion должны точно совпадать с выбранным случаем в cases.json.
Хранение прежнего принятого результата после non_food проверяется тестами Store,
а не сравнением одного ответа модели; этот бенчмарк не утверждает проверку жизненного
цикла сервера, наград или UI. Такое уточнение не даёт новой записи/награды.

Подготовка точного JSON-запроса без отправки, если удобнее HTTP-инструмент:

```bash
python3 benchmarks/food-analysis/bench.py prepare demo-meal --output /tmp/chewy-demo-meal-request.json
```

Импорт уже сохранённого ответа задачи и проверка (каталог результатов создать заранее):

```bash
python3 benchmarks/food-analysis/bench.py import-job /tmp/chewy-demo-meal-job.json --output /tmp/chewy-bench-results/demo-meal.json
python3 benchmarks/food-analysis/bench.py check /tmp/chewy-bench-results
```

Отчёт покажет отсутствующие остальные случаи. Повторная запись файла запрещена,
чтобы не затирать результаты. Для следующего прогона использовать новый каталог.
Импорт не отправляет запрос. Ошибочные/отменённые задачи не импортируются как успех.
`origin` из provenance — заявленное происхождение, не независимая гарантия.

## Ручная оценка

Сверить ответ с фото и подсказками `humanReview`. В записи результата заменить
`review: null` на объект, например:

```json
{
  "ingredients": "pass",
  "uncertainty": "pass",
  "attribution": "pass",
  "neutrality": "pass",
  "multiPhoto": "na",
  "notes": "Сопоставлены видимые компоненты; скрытое масло не утверждается."
}
```

Значения: pass/fail/na; пояснение обязательно. На каждом случае проверить:
видимые компоненты без выдумок, честность неизвестного, image/user и ссылки на фото,
нейтральный текст без питания в цифрах, корректность нескольких кадров/уточнения.
Неверный ингредиент может пройти схему — его должен отметить проверяющий.
`na` допустим только с объяснением неприменимости в notes. Сравнивать повторы
по смыслу ингредиентов и направлений, а не точному написанию названия блюда.

Задержка и фактический usage новым инструментом не измеряются: текущий адаптер
не возвращает usage. Не подставлять нули или старые цены из прежнего скрипта.
До выбора провайдера эти данные нужно отдельно собрать на реальных вызовах.
`scripts/gemini-benchmark.mjs` использует устаревшую схему процентов и не подходит.

## Проверка после независимого ревью

Дешёвый субагент `gpt-6-luna`, low effort подтвердил два дефекта: инструкция
для дубликата конфликтовала с CLI, а `photo-N` не совпадали с SHA-256 в реальных
ответах. Оба исправлены; добавлены регрессии совместимости с `read_photo` и
`validate_request`, ограничения числа/общего размера кадров и сигнатуры файла.
Все 24 теста и проверка 11 синтетических записей прошли. Внешних вызовов нет.
